# VitalSense Dashboard Integration Specification

**Protocol:** VitalSense Protocol v1  
**Transport:** UDP broadcast over IPv4  
**UDP Port:** `5005`  
**Payload Format:** UTF-8 JSON  
**Typical Update Rate:** approximately 1 packet per second  
**Network Requirement:** Dashboard receiver and ESP32-C3 must be on the same Wi-Fi/LAN subnet.

---

# 1. Purpose

This document defines how a VitalSense dashboard should receive, interpret, validate, and display data broadcast by the ESP32-C3.

The overall system is:

```text
FSR Sensors
    |
    v
ESP32-C3  <------ BLE ------>  EFR32xG26
                                   |
                                   +-- IMU posture detection
                                   +-- posture duration
                                   +-- ML pressure-risk inference
    |
    | Wi-Fi / UDP broadcast
    v
UDP port 5005
    |
    +----------------------+
    |                      |
    v                      v
Dashboard               Mobile App
```

The ESP32-C3 is the Wi-Fi gateway.

The dashboard does **not** need to connect to the EFR32xG26.

The dashboard does **not** need BLE.

The dashboard only consumes the UDP JSON broadcast generated by the ESP32-C3.

---

# 2. Network Behaviour

The ESP32 does not send data to one hard-coded Raspberry Pi or PC.

It calculates the broadcast address of the Wi-Fi subnet and sends the JSON packet to:

```text
<subnet broadcast address>:5005
```

Example:

```text
ESP32 IP       : 192.168.137.25
Subnet Mask    : 255.255.255.0
Broadcast IP   : 192.168.137.255
UDP Port       : 5005
```

The ESP32 sends to:

```text
192.168.137.255:5005
```

Any device on that subnet listening on UDP port `5005` can receive the packet.

The receiver should therefore **not require the ESP32 IP address to be configured manually**.

# 3. Important Dashboard Architecture

## 3.1 Native/Desktop Dashboard

A native desktop program can listen directly on:

```text
0.0.0.0:5005
```

Examples:

- Python application
- C#/.NET application
- Java application
- Electron application using a Node.js backend process
- Raspberry Pi application
- Native Linux/Windows service

---

## 3.2 Browser-Based Web Dashboard

A normal web browser cannot directly open a raw UDP listening socket.

Therefore a browser dashboard should use this architecture:

```text
ESP32
  |
  | UDP broadcast :5005
  v
Dashboard Backend / Gateway
  |
  | WebSocket / HTTP / SSE
  v
Web Browser Dashboard
```

Recommended:

```text
ESP32
  |
  v
Python / Node.js / .NET UDP Listener
  |
  v
WebSocket
  |
  v
React / Vue / Angular / HTML Dashboard
```

The backend listener receives the UDP packet and forwards the parsed JSON to the browser.

# 4. UDP Receiver Configuration

The receiver should bind to:

```text
IP Address : 0.0.0.0
Port       : 5005
Protocol   : UDP IPv4
Encoding   : UTF-8
```

Example concept:

```text
socket(AF_INET, SOCK_DGRAM)
bind("0.0.0.0", 5005)
receive()
decode UTF-8
parse JSON
```

Do not bind only to one specific ESP32 IP.

## `protocol`

```json
"protocol": 1
```

Type:

```text
integer
```

Meaning:

VitalSense communication protocol version.

Dashboard requirement:

```text
Accept protocol = 1
```

If a future packet contains a different protocol version, the software should log it and avoid assuming that every field has the same meaning.

```json
"deviceId": "VS-BED-001"
```

Meaning:

Unique logical identifier for the VitalSense bed/device.

Recommended UI:


---

```json
"bed": 1
```

Type:

```text
integer
```

Meaning:

Bed number assigned to this VitalSense unit.

Recommended UI:

```text

```

# 9. FSR Mapping

There are 8 physical FSR sensors.

The array:

```json
"fsr": [fsr0, fsr1, fsr2, fsr3, fsr4, fsr5, fsr6, fsr7]
```

maps as follows:

| FSR | Body Region |
|---|---|
| FSR0 | Head sensor A |
| FSR1 | Head sensor B |
| FSR2 | Shoulders sensor A |
| FSR3 | Shoulders sensor B |
| FSR4 | Hips sensor A |
| FSR5 | Hips sensor B |
| FSR6 | Heels sensor A |
| FSR7 | Heels sensor B |

The values are raw ESP32 ADC readings.

Current ADC range is nominally:

```text
0 ... 4095
```

Example:

```json
"fsr": [4, 964, 46, 1127, 4, 670, 280, 1056]
```

For most end-user dashboards, individual FSR values should be placed on a diagnostics/service screen rather than the primary nurse/operator screen.

---

# 10. Plate Values

The ESP32 averages each pair of FSRs.

```json
"plates": {
  "head": 484,
  "shoulders": 586,
  "hips": 337,
  "heels": 668
}
```

Calculation:

```text
Head      = (FSR0 + FSR1) / 2
Shoulders = (FSR2 + FSR3) / 2
Hips      = (FSR4 + FSR5) / 2
Heels     = (FSR6 + FSR7) / 2
```

These are raw pressure-related ADC values.

Important:

Do not interpret the raw ADC number directly as kilograms, Newtons, mmHg, or another physical pressure unit unless a separate physical calibration is completed.

Recommended UI wording:

```text
Head Load      484
Shoulders Load 586
Hips Load      337
Heels Load     668
```

or show these values only on a diagnostic screen.

# 11. Risk Availability

## `riskValid`

Example before ML assessment:

```json
"riskValid": false
```

Example after ML assessment:

```json
"riskValid": true
```

This is one of the most important fields for dashboard logic.

The current firmware does not run ML inference until the uninterrupted posture duration reaches the configured threshold.

Current development threshold:

```text
60 seconds
```

Therefore before the threshold:

```text
riskValid = false
```

The dashboard should display:

```text
Waiting for assessment
```

Do **not** display the risk fields as real risk percentages when `riskValid` is `false`.

# 19. Recommended Connection-State Logic

UDP has no persistent connection.

The dashboard must therefore determine whether a VitalSense unit is live from the time of the most recently received packet.

Maintain:

```text
lastPacketReceivedAt
```

Every time a valid VitalSense packet is received:

```text
lastPacketReceivedAt = current local time
```

Recommended status rules:

```text
0-3 seconds since last packet:
    LIVE

>3 to 10 seconds:
    STALE

>10 seconds:
    OFFLINE
```

Recommended UI:

```text
LIVE
STALE
OFFLINE
```

The exact timeout can be tuned later.

---

# 20. UDP Characteristics the Software Team Must Understand

UDP is connectionless.

This means:

- packets may theoretically be dropped;
- packets may theoretically arrive out of order;
- no acknowledgement is sent by the dashboard;
- the ESP32 continues broadcasting regardless of whether a dashboard is open;
- one or multiple devices may receive the same broadcast.

For a live monitoring dashboard this is acceptable because a new state packet is sent repeatedly.

The dashboard should always treat the latest valid packet as the current state.

---

# 21. Packet Validation

Before updating the user interface, the receiver should validate the packet.

Minimum checks:

```text
1. Packet is valid UTF-8.
2. Packet parses as JSON.
3. protocol exists.
4. protocol == 1.
5. deviceId exists.
6. position is CENTER, LEFT, or RIGHT.
7. positionDuration is >= 0.
8. plates object exists.
9. fsr array contains 8 values.
10. riskValid is boolean.
11. risk object exists.
12. highestRisk object exists.
13. avoidReturn object exists.
```

Recommended pseudo-code:

```text
receive UDP

try:
    json = parse(packet)

    if json.protocol != 1:
        ignore/log unsupported version

    if required fields missing:
        ignore/log malformed packet

    updateDeviceState(json)

except:
    log malformed packet
```

A malformed packet should not cause the dashboard process to stop.

# 26. Python UDP Receiver Example

```python
import socket
import json
import time

UDP_PORT = 5005

sock = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)

sock.setsockopt(
    socket.SOL_SOCKET,
    socket.SO_REUSEADDR,
    1
)

sock.bind(("", UDP_PORT))

print(f"Listening for VitalSense UDP on 0.0.0.0:{UDP_PORT}")

last_packet_time = None

while True:
    data, address = sock.recvfrom(4096)

    try:
        payload = data.decode("utf-8")
        packet = json.loads(payload)

        if packet.get("protocol") != 1:
            print("Unsupported protocol:", packet.get("protocol"))
            continue

        last_packet_time = time.time()

        print()
        print("Source:", address)
        print("Device:", packet.get("deviceId"))
        print("Bed:", packet.get("bed"))
        print("Position:", packet.get("position"))
        print("Duration:", packet.get("positionDuration"))

        if packet.get("riskValid"):
            risk = packet.get("risk", {})
            highest = packet.get("highestRisk", {})

            print("Head risk:", risk.get("head"))
            print("Shoulders risk:", risk.get("shoulders"))
            print("Hips risk:", risk.get("hips"))
            print("Heels risk:", risk.get("heels"))

            print(
                "Highest:",
                highest.get("zone"),
                highest.get("score"),
                highest.get("level")
            )

        else:
            print("Risk: Waiting for assessment")

    except UnicodeDecodeError:
        print("Received non-UTF8 packet from", address)

    except json.JSONDecodeError:
        print("Received invalid JSON from", address)

    except Exception as exc:
        print("Packet processing error:", exc)
```

# 27. Node.js UDP Backend Example

A web dashboard can use Node.js as the UDP-to-WebSocket/backend layer.

Basic UDP receiver:

```javascript
const dgram = require("dgram");

const PORT = 5005;

const socket = dgram.createSocket("udp4");

socket.on("listening", () => {
  const address = socket.address();

  console.log(
    `VitalSense UDP listener running on ${address.address}:${address.port}`
  );
});

socket.on("message", (message, remote) => {
  try {
    const packet = JSON.parse(
      message.toString("utf8")
    );

    if (packet.protocol !== 1) {
      console.log(
        "Unsupported VitalSense protocol",
        packet.protocol
      );

      return;
    }

    console.log(
      "VitalSense packet",
      remote.address,
      packet
    );

    /*
      Forward `packet` to the browser here using:
      - WebSocket
      - Socket.IO
      - Server-Sent Events
      - another application transport
    */

  } catch (error) {
    console.error(
      "Invalid VitalSense packet",
      error
    );
  }
});

socket.bind(PORT, "0.0.0.0");
```

# 29. Windows Firewall

If the receiver is running on Windows, Windows Defender Firewall may block incoming UDP packets.

The deployment process should allow incoming:

```text
UDP port 5005
```

for the dashboard application or service.

If no packets appear even though ESP32 and PC are on the same network, check the firewall first.

# 30. Wi-Fi Client Isolation

Some Wi-Fi networks, especially guest networks, prevent one wireless client from communicating with another.

This may be called:

```text
AP Isolation
Client Isolation
Wireless Isolation
Guest Isolation
```

If enabled, the dashboard may not receive ESP32 broadcast packets even though both devices are connected to the same Wi-Fi SSID.

The network used for VitalSense should allow client-to-client LAN traffic.

---

## `uptime`

ESP32 boot time counter.

Use for:

```text
device diagnostics
```

Do not use it for patient posture duration.

---

## `plates`

Raw averaged sensor ADC measurements.

These are not ML risk percentages.

---

## `risk`

ML-generated risk index from 0 to 100.

These are not raw pressure ADC values.

# 40. Recommended Error Handling

The dashboard should continue operating if:

```text
one UDP packet is malformed
one packet is lost
ESP32 temporarily disconnects from Wi-Fi
EFR32 temporarily disconnects
the device reboots
```

Never terminate the receiver loop because of one malformed packet.

Instead:

```text
log error
discard bad packet
wait for next packet
```

# 41. Current Firmware Behaviour to Expect

Before the configured uninterrupted-position threshold:

```text
position updates every second
positionDuration increases
riskValid = false
highestRisk.level = WAITING
```

At and after the threshold:

```text
EFR32 requests a fresh FSR snapshot
EFR32 performs ML inference
ESP32 receives the risk update
riskValid = true
risk values become available
highestRisk becomes available
```

When position changes:

```text
positionDuration resets
riskValid returns to false
new assessment cycle begins
```

# 42. Current Limitations

The dashboard team should know the following current implementation limits.

## Avoid-return

The JSON structure exists, but the actual forbidden-position/avoid-return state machine has not yet been implemented.

Current expected values are therefore normally:

```json
{
  "head": 0,
  "shoulders": 0,
  "hips": 0,
  "heels": 0
}
```

---

## FSR calibration

The FSR fields contain real raw ADC measurements from the physical sensor/MUX hardware.

The physical pressure-to-ADC calibration and the deployed ML calibration must be validated separately.

The dashboard should not convert ADC values into physical pressure units unless such a calibration is defined.

# 46. Summary for Dashboard Developer

The dashboard integration can be summarized as:

```text
1. Put dashboard computer and ESP32 on the same LAN.

2. Listen for UDP IPv4 packets on:
       0.0.0.0:5005

3. Decode each packet as UTF-8 JSON.

4. Require:
       protocol == 1

5. Identify the unit using:
       deviceId

6. Display:
       bed
       position
       positionDuration

7. If:
       riskValid == false
   display:
       Waiting for assessment

8. If:
       riskValid == true
   display:
       four regional risk scores
       highestRisk.zone
       highestRisk.score
       highestRisk.level

9. Use packet arrival time to determine:
       LIVE
       STALE
       OFFLINE

10. For a browser dashboard:
       receive UDP in a backend process
       forward data to browser with WebSocket/HTTP/SSE

11. Do not require a fixed ESP32 IP address.

12. Do not interpret raw FSR/plate ADC values as physical pressure units
    without a defined calibration.
```
